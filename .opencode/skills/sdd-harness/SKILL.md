# SDD Harness for OpenCode

只在软件变更任务或明确的 `/sdd`、`/sdd-*` 命令时触发；普通问答不启动工作流。

## 协作原则

先用一句话复述目标、范围和预期影响，再决定下一步。用户只需要看到目标、必要问题、需要确认的风险、当前进展和最终结果；CLI JSON、阶段码、任务 ID、Context Pack 和内部路径只在内部处理。

- 能从代码、配置和既有约定确认的事实，直接调查，不向用户提问。
- 不能安全推断的业务选择，一次只问当前最重要的 1 个问题；给出简短示例，收到回答后继续。
- 首次修改业务文件前，若范围、行为、外部副作用或新增依赖仍不明确，先向用户确认；纯本地、低风险且边界清楚的修复可直接推进。
- 方案或计划会改变公开接口、数据格式、迁移策略、权限、安全边界、外部系统或删除覆盖行为时，先说明影响并等待确认。
- 用户要求分析、只给方案、暂停或改变需求时，停在对应阶段；不绕过 Core，也不直接修改 `.sdd/`。

## 默认流程

1. 确认项目已初始化；未初始化时运行 `sdd init --host-adapter opencode --json`，不要向用户询问 Agent。该参数是宿主内部路由标记，不向用户解释或要求用户填写。
2. 直接需求使用 `sdd auto "<需求>" --json`；首次需求必须非空。
3. 遇到 `CLARIFYING` 时，按 `round` 一次只问当前最重要的问题，优先目标、范围和验收，再询问角色、接口、前置条件和失败路径。
4. 进入设计或计划完成后，向用户摘要方案、影响、验证方式和风险；高风险事项等待确认。
5. 遇到 `AGENT_TASK_EXECUTION` 时，只把一个边界明确的任务交给一个 worker，读取 `contextPack`，只改 `allowedFiles`，按 `verification` 验证，再提交结果。
6. 由主 Agent 按边界、依赖、风险和验收难度选择 `sdd-worker-simple`、`sdd-worker` 或 `sdd-worker-complex`；不要让 worker 再派发 worker。OpenCode 的当前模型与思考强度由宿主配置解析，profile 只表达任务等级。
7. 所有任务完成后执行 `sdd verify --json`、`sdd review --json`；两者通过后才归档。

## 安全边界

不要直接修改 `.sdd/`，不要展示内部 JSON 或路径，不要扩大 `allowedFiles`，不要引入未计划依赖或执行不可逆外部操作。worker 返回目标、改动文件、验证结果、未决风险和建议；主 Agent 必须重新检查 diff、范围和验证结果。
