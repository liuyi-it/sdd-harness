# 可用性试用与回归

本轮围绕一个真实的运费计算项目试用当前工作树的 `sdd` CLI。目标是让后续 Agent 能根据可复现的问题持续改善交付体验；长期产品约束见 [AGENTS.md](../AGENTS.md#项目最终目标)。

## 业务 demo

订单金额满 100 元免运费，不足 100 元收 10 元，负数金额抛出错误。实现只使用 Python 标准库。验收覆盖 0、99、100、101 和 -1 五个金额用例。

示例资产位于 [fixtures/usability](../fixtures/usability/)：

- `spec.json`：统一规格与技术设计。
- `plan.json`：一个包含测试、实现、验证的纵向任务。
- `test_shipping.py`：边界与错误测试。
- `shipping.py`：最终业务实现。

直接检验业务行为：

```bash
python3 -m unittest discover -s fixtures/usability -v
```

Windows 将 `python3` 换为 `python`。

## 重跑完整用户旅程

在本仓库执行：

```bash
cargo test -p sdd-cli --test usability -- --test-threads=1
```

需要 Rust 开发工具链、Git 和 Python。这个命令测试当前源码编译出的 CLI；不会替换 PATH 中已安装的 `sdd`，不会连接远端、调用模型或安装业务依赖。

测试为每次运行创建独立临时 Git 仓库，只通过 CLI 初始化、提交阶段结果、恢复行动、验证和归档。业务文件由测试扮演宿主写入，测试命令真实执行并收集退出码和输出，不直接调用 Core 或修改内部 Runtime。

覆盖的旅程：

1. 初始化项目，创建规格，读取状态并恢复同一规格行动。
2. 提交统一规格，获取包含全部任务字段的计划 Schema，并恢复等待中的计划。
3. 在计划等待时修订需求，再连续更正输入；确认最新输入生效、原验收仍在上下文中、旧计划不能越阶段提交。
4. 按真实 Python 命令提交计划，使用通配范围和空的额外禁止列表；遗漏必要字段时拒绝并保留可修正状态。
5. 派发任务并恢复同一任务。先写测试，真实观察模块缺失导致失败；再加入业务实现，运行两项测试覆盖五个金额用例并通过。
6. 回传实际命令输出和 Git 文件变化；参数边界与计划不符的结果被拒绝，正确结果被接受。
7. 执行质量门禁、检查任务进度、归档，验证归档包含需求和已完成任务数，并验证再次归档和项目空闲状态。
8. 创建多个需求，检查普通终端完整展示候选标题与标识，未选目标的写命令被阻止，明确目标后恢复正确行动。

## 试用发现与处理

| 试用问题 | 根因 | 当前处理 |
| --- | --- | --- |
| 计划返回的 Schema 不能指导 Agent 构造任务 | tasks 只声明普通对象，没有任务字段 | 复用并内嵌 task Schema，校验与下发共用同一份完整定义 |
| 构建结果需要反查源码才能填写 | 构建行动缺少结果 Schema | 直接下发 task-result Schema |
| Python 测试、带参数的 Rust 测试被阻止 | 门禁只接受四条完整命令字符串 | 按程序与质量检查入口校验，保留独立参数；补命令边界测试 |
| 具体新增文件落在允许的 glob 内仍报矛盾 | 计划按字符串相等比较，实施按 glob 匹配 | 计划与实施复用同一范围校验 |
| 计划等待期间无法修改需求 | 状态允许集合遗漏该阶段 | 允许修订并阻止旧计划越阶段提交 |
| 等待修订时再次输入被静默忽略 | 恢复分支优先于读取新输入 | 非空输入更新，无输入才恢复；同时带入修订前完整规格 |
| 状态信息过长时看不到候选，恢复要求手写 JSON | 文本模式倾倒/截断内部对象，next 指向占位结果提交 | 展示中文候选与任务进度，等待状态建议重新获取原行动 |
| 终端把上下文当结果展示，让人误以为会自动实施 | 用户输出与宿主协议未分开处理 | 普通输出说明等待宿主，完整上下文仅由 JSON 提供 |
| 归档中完成任务仍显示空复选框 | 不变的计划文档被当成实时进度表 | 计划保留任务定义，status 展示进度，归档记录完成任务数 |
| 用户需要不断催促切阶段或重复回答 | 模板未说明已有授权和后续阶段的关系 | 复用已有回答，完整实现请求按阶段持续推进；必要决策仍询问 |

## 人类交互专项验证

在完整交付流程之外，增加从普通用户角度的首次使用、错误恢复和阻断反馈验证。评判标准是能否看懂当前业务目标、原因和下一步，并按提示恢复正确任务；没有使用未经用户研究验证的量化体验评分。

| 场景 | 发现的问题 | 修复与验证 |
| --- | --- | --- |
| 首次使用 | 帮助只列工程命令；空项目误导为必须先配置 | 增加自然语言快速开始；空项目直接继续；目录结构选项真实传入规格行动 |
| 多任务选错阶段 | 建议丢失目标，跟随提示又触发歧义 | 恢复命令保留目标；测试按提示恢复同一变更 |
| 多任务冲突 | 只给内部标识，要求用户查看 JSON | 错误直接列业务标题和阶段；拼错标识时给可执行的查看命令 |
| 需求修订与归档查询 | 修订仍展示旧目标；已归档任务缺少标题 | 待修订标题取最新输入，所选任务摘要独立展示 |
| 质量失败 | 首次修复隐藏具体问题，阻断仅提示继续修复 | 真实 demo 添加计划外文件，验证首次修复、失败结果与状态都展示问题；手动恢复范围后普通验证通过 |
| 代码库诊断和长查询 | 输出内部 JSON，长结果被整体省略 | 缺少 CodeGraph 的独立进程验证可读诊断和 40 个文件的完整扫描结果 |
| Agent 向用户提问 | 没有明确要求业务语言和可理解选项 | Codex/OMP 五阶段模板明确按标题选择、说明取舍、报告阻断事实；结构校验通过 |

专项回归复用上面的 `cargo test -p sdd-cli --test usability -- --test-threads=1`，当前包含五项用户旅程测试。模板校验只证明结构有效，不能代替不同宿主和模型下的真实人类可用性研究。

全量验证同时定位到已有空查询降级测试的并行波动：模拟 CLI 的版本探测在 1 秒预算内未完成，尚未进入待验证分支。该测试的等待预算改为 10 秒，保留“已安装、查询空输出、正确降级”的断言，生产超时逻辑不变。

提交前另一项“命令成功但未生成索引目录”测试出现一次并行断言失败。已补充实际失败原因输出；随后连续五次定向测试和三次全量测试均通过，但未复现该次失败，不能据此宣称并行波动已彻底消除。该测试的时间预算和生产校验保持不变。

## 验证边界

手工试用由当前会话 Agent 驱动 CLI 完成，自动回归复用其业务案例验证协议和状态行为。自动回归不调用真实模型，因此不能证明所有模型、所有宿主会话都会正确理解模板；模板的语义、业务审查和用户体验仍需持续真实试用。

Core 检查结构、覆盖、文件事实与证据一致性，并不自行执行业务测试或证明自然语言验收已经满足。本 demo 的测试由宿主和回归程序实际执行。构建白名单也不是执行项目代码的安全沙箱。

全仓库交付检查：

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

可使用 `cargo test --workspace -- --test-threads=1` 串行复核外部工具相关测试。后续新增场景时，应扩展以上真实路径并检查相关文档，不能只增加预填成功结果的测试。
