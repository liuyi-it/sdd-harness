## 规格依据与提交前审查

先调查真实代码，再结合原始需求、用户历次回答和最新修订生成规格。代码与旧规格是待核对的材料，不是用户确认的替代品；不得修改业务文件。

### 区分依据

- 用户确认：记录用户明确提出、回答或明确授权自主决定的内容。推荐项、用户沉默、回答了同轮的另一题，都不等于接受建议；“继续”“生成方案”不自动确认尚未回答的业务取舍。
- 代码事实：注明文件、符号或接口文档依据，只证明现有实现是什么。复用旧接口前比较其过滤条件、时间窗口、阈值、权限和去重粒度是否符合新需求，不自动继承旧业务限制。
- 设计建议：明确这是 Agent 的方案及理由。授权内、不改变业务结果的实现细节可自主决定；会改变统计结果、范围、权限或验收的建议须得到明确回答后才能写成要求。
- 待确认：列明缺少什么、影响什么。影响正确性或实施的关键问题未解决时继续澄清，不回传正式规格；不能把阻塞问题藏进风险或默认值后宣称完成。非阻塞外部依赖可明确责任方与验证条件，不假定它已实现。

澄清过程中维护简短的“结论—来源—状态”记录，复用已有回答。上下文不足时先恢复可用会话或请用户补充，不虚构确认。对带有多个限定条件的回答，只确认用户实际回答的部分。

### 写入唯一规格

使用现有 resultSchema，不另造报告字段或第二份权威规格：

- requirements 的 statement 写清业务规则及关键依据（用户原话的简短转述或明确授权），scenarios 给出可验证的行为，不能为了补齐场景擅自增加业务口径。
- technicalDesign.currentState 只放已查证事实及出处；decisions 的 rationale 区分用户确认与 Agent 设计决定；interfaces 区分已验证的现有契约与拟新增或待外部验证的契约。
- 按任务需要交代标识的含义与映射、字段来源、存储和刷新方式，以及统计粒度、时间窗口、去重和过滤联动。不要把某个标识的选取规则推及所有关联数据。
- 需要跨系统联调的接口，应给出实施所需的字段类型、必填性、请求/响应例子与失败语义；无法验证的外部字段明确为拟议契约，不能伪称已有字段。简单或无接口变更的任务不强制扩展文档。
- “实时”“最近”“全部”等会影响验收的表述需转为可检查的边界；现有接口能力不足是设计差异，不能据此缩减用户要求。

### 提交前语义核对

完成草稿后，先对照原始需求及每轮用户回答检查，再调用结果回传命令：

1. 正向覆盖：每项已确认要求落到了需求和验收中，或有用户确认的排除依据；旧要求未被一条短修订意外丢弃。
2. 反向查据：每项业务限制、默认值、阈值、归因和去重规则都有明确来源；只有代码事实或 Agent 建议的不冒充用户确认。
3. 修订一致性：将旧结论逐项判为保留、替换或待确认；被否定的规则要同步从需求、验收、决策、接口、数据模型和测试策略中清除。旧规格即使已被 CLI 接收，也不能自动视为全部得到用户确认。
4. 边界与可实施性：需求与设计无矛盾，关键场景可执行，外部依赖的已验证部分和拟议部分清楚。发现会改变结果的缺口就继续澄清，不以字段齐全代替审查。

结束时简述已确认口径、Agent 自主设计和剩余非阻塞依赖，不让用户核对内部 JSON。Core 只验证结构、范围和一致性约束，不读取完整会话，也不判断用户是否真正确认；接收结果不代表语义审核通过，不得据此宣称所有需求已验证。
