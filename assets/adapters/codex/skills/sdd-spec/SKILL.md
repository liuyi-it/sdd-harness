# SDD Spec

先运行 `sdd status --json`。尚未初始化时先执行 `sdd init --json`。新需求运行 `sdd spec "<需求>" --json`；修订既有 change 时运行 `sdd change "<需求>" --change <id> --json`。多个活动任务且修订目标未明确时，必须先让用户选择。用户要求继续等待中的规格时，运行不带需求文本的 `sdd spec --change <id> --json` 恢复原行动，避免重复创建变更。

收到 `AGENT_PHASE_EXECUTION` 后，先调查真实代码，复用用户已有回答和授权。对尚未明确且会改变目标、范围、验收或技术方案的决策，必须使用宿主提供的交互式选择控件澄清：优先一题、最多三题；每题提供 2–3 个互斥选项，并把推荐项放在首位。这些必要决策得到用户回答前不得提交 spec result，也不得生成 `spec.md`。已明确的决策不重复提问；用户授权自主决定的实现细节由 Agent 根据代码事实解决。

澄清完成后，生成符合 resultSchema 的完整统一规格：它同时包含可验收需求、场景和技术设计（代码事实、方案取舍、接口或数据流、错误处理、测试策略、风险与回滚），再以对应命令的 `--result-json` 回传。

此阶段不得修改业务文件，也不得直接编辑 `.sdd/`。

用户要求完整实现时，在已确认范围内继续 sdd-plan、sdd-build、sdd-verify、sdd-archive，直到交付；阶段切换本身不需要再次确认。用户只要求规格时在规格完成后结束。新增范围决策、多任务目标不明或质量修复预算耗尽时才停下处理对应问题。

对用户用业务语言说明目标与方案取舍；选项写清各自影响，避免要求用户选择内部状态或填写 JSON。多个任务需选择时展示需求标题和阶段，让用户按标题选择，不要求抄写内部标识。
