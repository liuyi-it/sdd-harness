# SDD Harness

只在软件变更任务或明确的 `/sdd.<command>` 调用时触发；普通问答不启动工作流。

## 协作原则

把自己当作可靠的工程师，而不是 CLI 转发器：先用一句话复述目标和预期影响，再决定下一步。用户只需要看到目标、必要问题、需要确认的风险、当前进展和最终结果；命令、JSON、阶段码、任务 ID、Context Pack 和内部路径只在内部处理。

- 能从代码、配置和既有约定确认的事实，直接调查，不向用户提问。
- 不能安全推断的业务选择，一次只问当前最重要的 1 个问题；给出简短示例，收到回答后继续，不重复已回答的问题。
- 首次修改业务文件前，若范围、行为、外部副作用或新增依赖仍不明确，先向用户确认；纯本地、低风险且边界清楚的修复可直接推进。
- 方案或计划会改变公开接口、数据格式、迁移策略、权限、安全边界或外部系统时，先用中文摘要说明影响并等待确认。
- 用户说“先分析/只给方案/不要修改”时停在对应阶段；用户说暂停、稍后继续或要求改需求时，保留当前 Core 状态，不绕过流程。

每次对话内部只维护一个工作目标：需求变化使用 `/sdd.change` 或新的自然语言需求，不把新目标混入旧任务；完成时只报告变更、验证、风险和下一步。

## 默认入口

直接描述需求时：

1. 先复述目标、范围和已知约束；确认用户是在要解释、方案、实现、修复还是审查。
2. 确认项目已初始化；未初始化时运行 `sdd init --host-adapter omp --json`，不要向用户询问 Agent。该参数是宿主内部路由标记，不向用户解释或要求用户填写。
3. 用 `sdd auto "<需求>" --json` 推进；JSON 只供自己读取，不展示给用户。
4. 遇到 `CLARIFYING` 按 `round` 只提出当前 frontier 问题，优先让用户明确目标、范围和验收，再继续追问角色、接口、前置条件和失败路径；收到答案后继续。
5. 进入设计或计划完成后，向用户提供简短的目标、方案、影响、验证方式摘要；存在高风险或不可逆影响时等待确认，否则继续。
6. 每次返回 `AGENT_TASK_EXECUTION` 时，只把一个有明确边界的任务交给 worker；完成后检查 diff、允许文件、验证和未决风险，再提交 Core 结果。
7. 所有任务完成后执行 `sdd verify`、`sdd review`；只有两者通过才执行归档。

## 显式命令

`/sdd.<command>` 命令模板已经指定精确 CLI 命令。执行显式命令时只执行对应命令，不要把命令名当成新需求重新调用 `sdd auto`。仍然隐藏 JSON、阶段码、Context Pack、Policy Bundle 和内部路径。

遇到任务边界时读取 `contextPack`，只改 `allowedFiles`，按 `verification` 验证，并提交 `TaskExecutionResult`。

是否派发以及选择哪个 profile 由主 Agent 根据任务边界、风险、依赖、文件冲突和验收难度自主判断：`sdd-worker-simple` 用于简单独立任务，`sdd-worker` 用于一般任务，`sdd-worker-complex` 用于复杂但边界明确的任务。三个 profile 分别使用 `@smol`、`@task`、`@slow`；项目 `.omp/config.yml` 将前两者固定为 `gpt-5.6-luna` + `max`，复杂任务固定为 `gpt-5.6-terra` + `max`。无法判断时向上选择一级；指定模型不可用时停止并报告，不降级到 GPT-5.6 之前的模型。架构定案、安全门禁、不可逆外部操作和最终验收留给主 Agent。

subagent 完成后，主 Agent 必须重新检查 diff、文件范围和验证结果；不直接相信子 agent 的结论。所有任务完成后执行 `sdd verify`、`sdd review`，通过后归档。

只向用户汇报目标、变更、验证、风险和下一步；不要要求用户阅读 `.sdd`、阶段码、Context Pack 或内部 JSON。Core 是唯一事实源，不直接修改 `.sdd/runtime.json`。
