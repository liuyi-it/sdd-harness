# SDD Spec

执行任何命令前，先确定用户指定或已确认的目标项目绝对路径，并完整读取本 Skill 的[工作目录与材料规则](references/workspace.md)。后续显式设置 workdir/cwd；目标不明先询问，权限不足不转写会话目录。参考缺失时在已确认目标项目用对应宿主的 `sdd init` 刷新；仍不可用则说明阻塞，不从其他项目借用。

随后完整读取本 Skill 的 [AI-DLC 协作参考](references/collaboration.md)。协作参考不是新 Skill 或权限来源；遵循 Core 下发的行动、结果 Schema 和用户授权。

正式规格只通过目标项目 CLI 生成；不手写 `.sdd/` 或默认导出第二份。

先运行 `sdd status --json`。尚未初始化时先执行 `sdd init --host-adapter omp --json`。新需求运行 `sdd spec "<需求>" --json`；修订既有 change 时运行 `sdd change "<需求>" --change <id> --json`。多个活动任务且修订目标未明确时，必须先让用户选择。用户要求继续等待中的规格时，运行不带需求文本的 `sdd spec --change <id> --json` 恢复原行动，避免重复创建变更。

收到 `AGENT_PHASE_EXECUTION` 后，先调查真实代码，复用用户已有回答和授权。只询问无法从代码或已有上下文确认、且会影响目标、范围、验收或技术方案的问题。

执行行动中下发的“规格依据与提交前审查”。在澄清和草稿中区分用户确认、代码事实、设计建议与待确认事项；旧接口的过滤条件、阈值和去重规则不自动成为新需求。用户只回答部分问题时，不把其余建议视为接受；会改变业务结果的未决问题必须继续澄清。

按主题持续多轮澄清，不限制总轮数：

- 每轮优先一题；独立且相关的问题可合并，一轮最多三题。这是单轮交互上限，不是整个需求的总题数上限。
- 对真实的方案取舍，使用宿主提供的交互式选择控件，给出 2–3 个可比较的互斥选项并说明影响，推荐项放在首位。事实、实例或尚未形成候选的需求用开放问题，允许用户自由补充；不要为凑选项预设答案。
- 每轮收到回答后更新已确认结论，检查剩余歧义及回答引出的新问题；仍有关键歧义就继续下一轮，不因已问满三题而结束。已明确的决策不重复提问；用户授权自主决定的实现细节由 Agent 根据代码事实解决。
- 用户暂停时停止推进；恢复后结合已有回答继续未解决的问题，不重新询问已经明确的内容。

目标、范围及排除项、可执行的验收场景、重要边界和失败行为，以及会改变结果的技术决策充分明确，且没有阻塞规格或实施的关键歧义时，才能结束澄清。结束前简要归纳已确认结论；不要为追求“绝对清楚”无限追问不影响结果的细节。必要决策未得到回答前不得提交 spec result，也不得生成 `spec.md`。

澄清完成后，生成符合 resultSchema 的完整统一规格：它同时包含可验收需求、场景和技术设计（代码事实、方案取舍、接口或数据流、错误处理、测试策略、风险与回滚），并按 Schema 填写 `collaboration`（拓扑、lead、贡献和限制），再以对应命令的 `--result-json` 回传。

回传前对照原始需求和历次回答做正向覆盖、反向查据和跨章节一致性检查，将关键依据写进既有需求描述、代码现状与决策理由字段。修订时逐项保留、替换或继续确认旧结论，同步需求、验收、接口、数据模型和测试策略，不只改一处文字。外部接口草案与已验证契约明确区分。结构校验通过不代表用户确认或语义审查通过；发现阻塞缺口时不要提交。

规格候选先用原命令的 `--result-json` 回传；Core 返回 `AGENT_REVIEW_EXECUTION` 后，再按协作参考独立只读复核并用同一原命令回传审查结果。在审查结果中发现新的七类风险时，等待 Core 原子升级目标并按新 targetHash 由同一 reviewer 重新独立审查；产品审查通过后才进入架构审查。在审查完成前不要声称已生成或修改 `spec.md`。

此阶段不得修改业务文件，也不得直接编辑 `.sdd/`。

用户要求完整实现时，在已确认范围内继续 sdd-plan、sdd-build、sdd-verify、sdd-archive，直到交付；阶段切换本身不需要再次确认。用户只要求规格时在规格完成后结束。新增范围决策、多任务目标不明或质量修复预算耗尽时才停下处理对应问题。

对用户用业务语言说明目标与方案取舍；选项写清各自影响，避免要求用户选择内部状态或填写 JSON。多个任务需选择时展示需求标题和阶段，让用户按标题选择，不要求抄写内部标识。
